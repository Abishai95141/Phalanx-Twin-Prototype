## The question

Which backend should the build's compiled hot loops use: **Numba**, **JAX on CPU**, or a **hybrid** (Numba
time-stepping + JAX for calibration gradients)? Decide on measured evidence.

## Workload: a representative mini-model

Not a toy: it must stress what the real M07/M08/M03 loop will stress.
- **Plant:** a two-spool rotor model.
  - N1, N2 rotor ODEs with torque maps as small 2-D lookup tables with interpolation;
  - fuel-flow actuator lag;
  - EGT first-order thermal response with a mass-flow-dependent τ (τ ∝ W^-0.5);
  - a metal-temperature state.
- **Controller:** a closed-loop governor (M08-like). PI on N2 error, with MIN/MAX limiter selection (accel/decel schedules as tables).
- **Disturbances:** per-unit process disturbances (AD-32): AR(1) or a filtered-noise state per engine.
  - Draw them from **pre-generated keyed blocks** (NumPy SeedSequence → Philox, keyed by unit) fed into the compiled loop. Also try in-loop generation if a backend makes that natural.
  - **Report whether RNG can stay backend-independent this way.** That matters for CRN and forks.
- **Sub-stepping:** 240 Hz outer step, with ≥ 2 inner sub-steps for the stiff states.
- **Snapshot:** state is a small set of arrays. Show snapshot/restore mid-run gives bitwise-identical continuation per backend.

Write a **NumPy reference implementation** first. Every backend must match it: bitwise where achievable, otherwise
within a stated tolerance with the reason (e.g. FMA / fastmath). Keep fastmath **off** unless it is bitwise-safe,
and report what each backend does by default.

## Measurements

Record machine info, versions, threads and the **sample size / repetitions** for each.

| ID | Measurement |
|---|---|
| M1 | Single sortie-hour (864,000 outer steps) wall time per backend; × real-time factor (target ≥ 50× real time for the full telemetry chain, so the engine loop alone must be far faster) |
| M2 | Compile / JIT overhead (cold and warm), and the cache options (Numba `cache=True`, JAX persistent cache) |
| M3 | Batch of 1,000 units for a shorter horizon (e.g. 60 s) via `prange` / `vmap`, plus thread scaling (1, 2, 4, 8 threads) |
| M4 | Determinism: bitwise identical across repeated runs, across processes, single vs batched execution, and thread counts |
| M5 | Gradients for calibration (AD-34): JAX `grad`/`jacfwd` through a 30–60 s transient window vs Numba finite differences. Wall time and accuracy, against a complex-step or high-precision FD reference |
| M6 | Memory footprint (peak RSS) per configuration |
| M7 | Code ergonomics: lines of code, debuggability, how table lookups and limiter MIN/MAX selection express in each, and how "pure step function over explicit state" maps to each |
| M8 | Usage-mode relevance: a sortie-summary surrogate evaluation for 30 tails × 2 years. Rough estimate only; don't over-build |

**Process:**
- Start small (a 10 s horizon, 1 unit). Verify against the NumPy reference, then scale. Log each check (sample → verify → scale).
- **Keep RAM under ~4 GB and limit threads to ≤ 4** for most runs: other agents share this machine. Run the thread-scaling sweep once, briefly.
- No Kaggle needed; if you think it is, stage per `_common.md`.
