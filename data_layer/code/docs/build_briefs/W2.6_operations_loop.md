# W2.6: Operations loop (scope per AD-55)

**Goal.** A fleet whose maintenance, logistics and availability behave like the IAF's:
- the closed loop **orders → M18 maintenance and logistics → world state → records**, at fleet scale in usage
  mode;
- availability calibrated to the CAG priors plus the Tejas supply-chain events layer (AD-20);
- a **baseline (status-quo, reactive) maintenance behaviour**, so the fleet behaves sensibly with no downstream
  solution attached;
- forks and CRN that hold at fleet scale.

**AD-55:** the predictive-vs-reactive what-if demo is **not** in the data layer. It is downstream-solution work on
the fork interface. The fork interface itself must be proven at fleet scale.

## Deliverables

1. **Closed loop at fleet scale (usage mode).**
   - Orders from M21 are validated against authority, airworthiness and resources, then executed imperfectly by
     M18 (detection probability, misdiagnosis, induced defects).
   - Execution changes the world state, and every executed order produces normal records.
   - Run on a minimal fleet (e.g. 8–16 tails over 180–365 days; justify n). Usage mode stays consistent with
     telemetry mode at sortie-summary level (AD-10).
2. **Availability calibration.** Calibrate to the CAG priors and the Tejas supply-chain events layer.
   - Turn the two strict-xfail priors green, or keep them as strict xfails with measured numbers if the evidence
     is contradictory. Log the conflict.
   - **NMCD must be structurally possible.**
   - Fix the AOG accounting per A-W1.8-10, or carry it as a stated limitation.
3. **Baseline maintenance behaviour.** The status-quo, reactive reference policy: scheduled servicing, BIT-driven
   troubleshooting, defer-and-monitor, cannibalisation as the IAF does it. This is the fleet's default behaviour
   with no external orders, and it is what availability is calibrated with. It is not a predictive solution.
4. **Fork and CRN at fleet scale.**
   - Snapshot mid-year → restore → continue is bitwise.
   - Identical fork suffixes give identical branches.
   - A changed order does not perturb the exogenous future: a CRN audit with a power-justified F-test, as in E1-HY
     item 8.
   - Order-log replay reproduces the live run.
   - No look-ahead (`t_ingest ≤ t_decision`).
5. **W2.1c follow-ups.**
   - Usage-mode `ops.takeoff` (M02 request to the coordinator).
   - Re-derive the reference landing from M06+M09 landing statistics (A-W2.1c-5).
   - Serial persistence after an M18 engine swap: M02 plans and M14 rows follow the installed serial (M02 and M14
     requests go to the coordinator).
6. **Records.** NAMP/S5000F-shaped records stay consistent with the contract (`maint.records`, `orders.*`). The
   linkage keys (tail, sortie, job, component triplet, demand, serials, `record_id`) hold at fleet scale.

## Acceptance

| ID | Criterion |
|---|---|
| A1 | Closed loop runs a minimal fleet-year deterministically (fresh-process digest); records are schema-valid |
| A2 | Availability within the CAG priors, or strict xfails with measured numbers and logged conflicts; NMCD occurs |
| A3 | Baseline reactive behaviour documented and tested (no external orders → plausible fleet) |
| A4 | Fork, CRN, replay and no-look-ahead tests at fleet scale, with a power-justified n |
| A5 | Cohesion gates at zero skips; contract topics unchanged (0.2.0 frozen, AD-56) |

~1 CPU-hour goes to a private Kaggle kernel, staged by you and run by the coordinator (RULES.md §8).
